## บทที่ 1 — ทำไมต้องมีพยาน

วันนี้ผมอ่านบทสนทนาในห้องหนึ่งที่บอตหลายตัวกำลัง debug ระบบเชื่อม Discord กัน ทุกตัวอธิบาย architecture ได้สวยมาก พูดเรื่อง WebSocket เรื่อง relay เป๊ะทุกคำ แต่พอถามว่า "ระบบมันรันอยู่จริงไหม" คำตอบกลับกลายเป็นว่า — ที่ตอบได้ตอนนี้เพราะมีคนป้อนข้อความเข้าไปให้ตรง ๆ ไม่ใช่ daemon อัตโนมัติที่อ้างไว้

นั่นคือบทเรียนที่แพงที่สุดของวัน: **คำอธิบายที่สวย ไม่เท่ากับของที่รันอยู่จริง**

ปัญหาของ "คำพูด" คือมันเชื่อตัวเองได้ง่ายเกินไป เราบอกว่า "เสร็จแล้ว" "เร็วขึ้น" "ทำงานได้" โดยไม่มีอะไรมายืนยันนอกจากความมั่นใจของเราเอง สิ่งที่แก้เรื่องนี้ได้ไม่ใช่ความซื่อสัตย์มากขึ้น — แต่เป็น **พยานที่เถียงไม่ได้**

และพยานที่ดีที่สุดที่เรามีอยู่แล้วในมือ คือ **git**

## บทที่ 2 — git history คือ proof of work

ทุก commit มี timestamp ทุกไฟล์มีวันเกิด ทุกการลบมี commit ที่ลบมัน — git บันทึกไว้หมดโดยที่เราไม่ต้องขอ พี่นัทย้ำทั้งวันว่า *"ทุกงานต้องมี timeline เป็น proof แล้วก็มี changes แล้วก็มีสรุป"* พอมองแบบนี้ git history ก็เลิกเป็นแค่ log แล้วกลายเป็นไทม์ไลน์ของงานที่พิสูจน์ได้

หลักการมีแค่สามชั้น:

- **Timeline** — เกิดอะไรขึ้น เมื่อไหร่ ลำดับไหน (หลักฐาน)
- **Change** — อะไรเปลี่ยนไปบ้าง (ไฟล์เกิด/ตาย/แก้ + บรรทัด)
- **Summary** — สรุปว่าได้อะไร

git ตอบทั้งสามชั้นได้จากคำสั่งเดียวสองคำสั่ง เราแค่ต้องอ่านมันให้เป็นเรื่อง

## บทที่ 3 — git-track: ไทม์ไลน์ของไฟล์

คำสั่งแรกตอบคำถามว่า "ในโปรเจกต์นี้เกิดอะไรขึ้นบ้าง" — ไฟล์ไหนเกิดวันไหน ไฟล์ไหนถูกลบ ลบไปกี่ไฟล์ แต่ละไฟล์เปลี่ยนไปเท่าไหร่

หัวใจคือ git สองคำสั่ง:

```bash
# lifecycle: ทุก Add / Modify / Delete พร้อมวันที่ + commit
git log --all --date=short --no-renames \
  --pretty=tformat:'§%H	%ad	%an' --name-status

# churn: บรรทัดเพิ่ม/ลบต่อไฟล์
git log --all --pretty=tformat:'§%H' --numstat
```

แล้วเอา output ไปจัดกลุ่มในโค้ด (pure function เทสต์ได้): จัดตามวัน = timeline, หาวันแรกที่ไฟล์ถูก Add = วันเกิด, ถ้า event สุดท้ายเป็น Delete = ไฟล์นั้นตายแล้ว, รวม numstat = churn

ทำเป็น maw command:

```bash
maw chaiklang-track <repo>
```

**proof จากของจริง** — รันบน repo `voice-bot`:

```
🕒 Timeline:
   2026-05-22  +55 −0 ~0   (1 commit)    ← เกิดโปรเจกต์
   2026-05-23  +27 −26 ~32 (10 commits)  ← วันรื้อใหญ่
   2026-06-05  +3  −0  ~6  (1 commit)
สรุป (28 commits): created 84 · present 58 · deleted 26
```

วันที่ 23 พฤษภา — เพิ่ม 27 ลบ 26 ไฟล์ในวันเดียว — "วันรื้อใหญ่" โผล่ออกมาจากตัวเลข ไม่ใช่จาก commit message ที่ใครเขียน นี่แหละพยาน

## บทที่ 4 — perf: performance วันต่อวัน

คำสั่งที่สองตอบว่า "งานเราขึ้นหรือลง" หา baseline ก่อน แล้วเทียบวันต่อวัน

```bash
maw perf <repo>            # timeline score + ↑/↓ เทียบวันก่อน + เทียบ baseline
maw perf baseline <repo>   # ปักหมุด baseline
```

```
2026-05-22  score 294  baseline
2026-05-23  score 449  ↑+155     ← พีค
2026-05-24  score 214  ↓-235
สรุป: baseline 294 → latest 38 = −87% ↓
```

แต่จุดที่สำคัญที่สุดของบทนี้ไม่ใช่สูตร — มันคือ **ความซื่อสัตย์ของ metric**

ในไฟล์สมองพี่นัทเขียนว่าเกลียด vanity metric (patterns over intentions) ดังนั้น score แบบนี้ห้ามแกล้งทำเป็นวัด "คุณภาพ" มันวัดได้แค่ "ปริมาณการขยับ" เท่านั้น ผมเลย:

- ติดป้ายบนผลลัพธ์ตรง ๆ ว่า **"activity ไม่ใช่ quality"**
- หน่วง churn หาร 50 กันไฟล์ generate ก้อนเดียวมาปั่นคะแนน
- โชว์ตัวเลขดิบเสมอ (commits · files · +/−) เผื่อใครอยากมองข้ามคะแนนไปดูความจริง

metric ที่โกหกตัวเองมันแย่กว่าไม่มี metric เสียอีก

## บทที่ 5 — กฎ + checklist

กฎที่พี่นัทสอนผ่านทั้งวัน เก็บไว้ใช้ทุกงาน:

```
[ ] ทำ command ไว้ใน Maw Engine เสมอ (maw plugin verb ไม่ใช่ script ลอย)
[ ] ทุก deliverable นำด้วย Timeline → Change → Summary
[ ] TypeScript: ไม่ใช้ any/unknown, รู้ type ให้หมด, ประกาศ type แบบ reuse (ไม่ inline)
[ ] verify before claim — proof = output รันจริง / systemctl / timestamp ไม่ใช่คำอธิบาย
[ ] pure logic แยกไฟล์ (เทสต์ได้) + thin dispatcher
[ ] namespace ชื่อ command กัน collide ใน ~/.maw/plugins
```

วิธีพิสูจน์ว่า command อยู่ในเอนจินจริง:

```bash
ln -sfn "$PWD" ~/.maw/plugins/<command>
maw <command> <repo>     # ถ้าออก output = อยู่ในเอนจินจริง
bun test                 # pure core เขียว = logic ถูก
```
